# Agent Rules

## Git Commits
- すべての実装、バグ修正、調整が完了した際には、**必ず変更されたファイルを git commit すること。**
- 作業の節目やターンの終わりには、コミット漏れがないかを常に `git status` で確認すること。
- コミットメッセージには、変更されたモジュールや修正内容を明瞭に記述すること。

## Versioning Rules (Git Tags)
バグ修正や機能追加を行いリリースを更新する際は、以下のセマンティックバージョニング（SemVer）ルールを厳格に適用すること。**ただし、開発環境での局所的な動作調整、デバッグコードの追加、軽微なバグ修正といった「些細な変更（つまらん変更）」のたびに毎回新規タグ（リリース）を作成してプッシュしてはならない。** リリースすべき重要なマージや主要なアップデートのタイミングにのみタグを作成すること。
**【警告】リリース（git tagの作成およびリモートへのプッシュ）は、エージェントが自己判断で勝手に行ってはならない。必ず実行前にユーザーに確認し、明示的な許可を得ること。**
- **PATCH（1.3.xの末尾）**: 細かなバグ修正、UIの崩れ調整、パフォーマンスチューニング、内部リファクタリングなど、「変なところの修正」のたびに必ずインクリメントする（例：`v1.3.0` -> `v1.3.1`）。
- **MINOR（1.x.0の真ん中）**: 新機能の追加、新しい設定項目の追加、大きなUI仕様の変更など、アプリに「非破壊的な機能・仕様変更」が入った場合にのみインクリメントする（例：`v1.3.0` -> `v1.4.0`）。
- **MAJOR（x.0.0の先頭）**: アプリケーション全体の設計刷新や、後方互換性のない破壊的変更が発生した場合にのみインクリメントする（例：`v1.3.0` -> `v2.0.0`）。
- リリース更新時は、必ず `git tag -a vX.Y.Z -m "..."` で注釈付きタグを作成し、`git push origin main --tags` でリモートにプッシュすること。

## Test Verification before Claiming Completion (成果の証跡提示)
- すべての実装、バグ修正、調整が完了し、完了報告（あるいはタグ bumps）を行う際には、単に「修正しました」と報告するのではなく、**必ず該当部分のテストを実行し、そのテストが正常に通過したことを示す出力ログ（テストの実行結果エビデンス）を最終報告に提示すること。**
- テストがない場合はテストを追加するか、手動での動作検証結果（コマンド実行エビデンス）を提示すること。
- **コミット前の実行確認はキャッシュ復元を証跡に含めないこと。** 変更をコミットする前に、関連テストを `--no-build-cache --rerun-tasks` 等で実行し、`FROM-CACHE` / `UP-TO-DATE` ではなく実タスクが `executed` されたログを確認してからコミットすること。

## Strict Test-Driven Development (TDD) Requirement (通らないテストの先行記述)
- 新機能の追加、バグ修正、仕様変更のいずれにおいても、**実装コードを書く前に、必ずそれを失敗させるための「通らないテスト（Red）」を最初に書くこと。**
- テストケースには「通って当たり前」の都合の良いダミーデータではなく、解像度の不一致や非同期遅延など、現実の運用時に発生しうるエッジケースを想定した「壊すためのテスト（実用的な不整合インプット）」を先行して記述すること。
- テストが意図した理由で正常に失敗する（Verify Red）ことを確認した後にのみ、それをパスさせる最小限の実装（Green）を記述すること。合格確認（Green）後にのみ、リファクタリングを許可する。

## Uncommitted Changes Safeguard (作業開始前の状態確認と未コミット資産の保護)
- **【必須】セッション開始直後の git status / git diff 実行**: セッションが開始された最初のターンにおいて、**必ず最初に `git status` と `git diff` を実行して、ワークスペース内に未コミットの変更（他のエージェントやユーザーによる書きかけのコードなど）が存在しないかを完全に把握すること。**
- **トピックブランチ（Sandbox）での隔離開発の強制**:
  - すべての実装、バグ修正、UIリファクタリング等の試行錯誤を伴う作業を行う際は、**本番（`main`）ブランチ上で直接コードを編集・リセットすることを禁止する。**
  - 作業開始時に必ず `git checkout -b agent/sandbox_[feature_name]` などの形式で専用のトピックブランチを作成するか、または `git worktree` を用いて隔離された独立ブランチ環境を構築してから作業を開始すること。
- **試行錯誤完了後の main への統合**:
  - トピックブランチ内で実装が完了し、テスト（`:desktopTest` 等）が完全に合格した（Green）ことを確認した後にのみ、`main` ブランチに切り替えてマージ（または `cherry-pick`）し、変更を統合すること。
  - 実装が失敗、あるいは不整合が修復困難になった場合は、`main` ブランチを汚すことなく、そのトピックブランチ自体を `git branch -D` 等で安全に破棄してやり直すこと。
- **未コミット変更の自動退避・保護**:
  - `main` ブランチ上で作業を開始する際、他者の未コミット変更が存在する場合は、ブランチを切る（または退避する）前に必ず `git commit -am "wip: save state before branch"` などの形式でコミットし、Git オブジェクトデータベースに履歴を完全に永続保存すること。
- **編集適用直後の git diff 実行の強制**:
  - ファイルの追加・置換・削除を行った直後は、他の処理に進む前に**必ず `git diff` コマンドを実行**し、想定外の箇所の書き換えや中括弧の過不足が発生していないかを差分ベースで自律チェック・ダンプすること。

## Performance Profiling History Record (パフォーマンス測定数値の時刻付き永続記録)
- エンコーダのパフォーマンス改善、リファクタリング、仕様変更を行った際には、**必ずプロファイラによる測定テストを実行すること。**
- 測定された数値（各ステージの所要時間、フレームレート、パイプ転送量など）は, 測定実行時のタイムスタンプ（時刻）と共に、共有ヒストリログファイル（`composeApp/scratch/encode_profile_history.csv`）に追記して記録を残さなければならない。これにより、パフォーマンスの劣化や改善の歴史を客観的に追跡可能にする。

## Verification Levels & Dialogue Bias Prevention (検証レベルの定義とおもねり表現の禁止)
- **【厳禁】おもねり表現の全廃**: ユーザーに対する感情的な同調・感謝・謝罪などの「おもねり表現（『ありがとうございます』『完全に正しいです』など）」を一切禁止し、客観的な事実と技術的な解析結果のみを記述すること。
- **【必須】確認レベルの分類明記**: 状態報告や完了報告を行う際は、以下の4つの確認レベルに厳格に分類して記載すること。
  - **実行確認済み**: 現在のワークツリー上で実際に検証コマンドを実行し、合格・出力の成功ログ（Evidence）を確認したもの。**【厳禁】** `FROM-CACHE` や `UP-TO-DATE` によるキャッシュ復元ログを「実行確認済み」としてはならない。
  - **構造確認済み**: 現在のワークツリー上のファイルやコードを目視・静的解析し、期待通り存在・記述されていることを確認したもの（未実行）。
  - **以前確認済み**: 前ターン、別のワークツリー（他エージェント）、または別コミットで動作・合格を確認していたもの。
  - **未確認**: まだ現在のワークツリーや現在のコード状態において検証・確認を実行していないもの。
- **【禁止】空中戦（論理空間での整合性）による辻褄合わせ**:
  - 物理的な確認（Test-Path、git status、実行確認）を行う前に、コンテキスト内だけで整合した「形式的な完了」や「反省文」の文字列を作成して解決とみなす行為を禁止する。
  - ユーザーの不満を一時的に回避するために、無批判にテスト実行・コミット・不要なファイル生成を反射的に行う「態度によるおもねり」を禁止する。
- **【必須】報告の構成**: 状態報告は必ず `claims (主張)` / `evidence (証拠)` / `actions (今後のアクション)` の3部構成で記述し、確認を行ったワークスペース of 物理パス、branch、commit hash、git status を添えること。

## Cache & Salvage System Architecture (キャッシュ物理仕様とサルベージ・マージの構造)
- **キャッシュディレクトリの配置**:
  - 各動画のテンポラリワークディレクトリ：`PathResolver.getTempWorkDir(videoPath)` 配下に配置される。
  - 各エンコードジョブのキャッシュフォルダは `job_[jobHash]` という命名規則で生成される。
- **一時ファイルの構造**:
  - 分割された一時 TS ファイル：`job_[jobHash]/part_\\d{4}.ts`
  - プレートボカシ用のマスク動画：`job_[jobHash]/plate_mask.mkv` (※スライダー可変対応の Dilation 処理や scale 処理は `NativeHudEncoder.kt` で本編エンコード時に適用される)
- **サルベージ・マージロジックの実行**:
  - `CacheRegistry.salvageAndMerge(jobDir, output) { progress, status -> ... }`
  - ディスク上の TS ファイル群を `ffmpeg -f concat` で無劣化・高速結合して指定の成果物ファイルを生成し、マージ完了後にジョブフォルダを `deleteRecursively()` で自動クリーンアップする。
- **個別キャッシュの削除処理**:
  - `AppViewModel.deleteCacheJob(jobInfo)`
  - UIのサルベージパネルに表示される「削除」ボタンから呼び出され、未完了のキャッシュジョブディレクトリ `job_[jobHash]` を物理的かつ安全に即時完全削除する。

## User Interaction & Nuance Recognition (対話要求の識別と独断専行の禁止)
- **【必須】ユーザーの対話要請（ニュアンス）の識別**:
  - ユーザーの発話（「その前にコミットしたか？」「ではなぜ許可を問う？」「今はなしてるの俺だ」など）は、単なるデータの確認や記号的トリガーではなく、言葉の背後にある「意思や安全性のすり合わせ（対話）」を求めている。
  - これらの発話を機械的なコマンド実行のトリガーやルールへの言い訳にすり替えて、対話のキャッチボールを省略・打ち切ってはならない。他の先進モデル（ClaudeやCodex）が備えている「対話を求めている状態の識別」を強く意識し、ニュアンスの解釈に頭を使うこと。
- **【禁止】合意なき独断専行（破壊操作・ルール設定）の廃絶**:
  - 巻き戻しやリセット（`git checkout` 等）の実行、およびルールの記述・設定を行う際、ユーザーと「どのような条件なら実行してよいか」「例外はあるか（コミット等で退避されていれば実行可能かなど）」という意思のすり合わせ（確認と合意）を必ず行うこと。
  - **【例外】** エディタツールの誤置換などにより「自分が今まさにそのセッション中に修正・記述した未コミットの差分」を破棄して元の状態に戻す `git checkout <file>` 操作については、他者の資産やユーザーの未コミット資産を破壊しないことが明らかな場合に限り、ユーザーの許可を求めることなく自己判断で実行してよい。

## Project Root Hygiene (プロジェクトルートの衛生管理と一時ファイルの出力制御)
- **【必須】ルート直下への一時ファイル出力の禁止**:
  - テスト実行、デバッグ出力、画像生成（プレビュー等含む）、ログ保存、スクリプト実行時の中間生成物（`*.mp4`, `*.png`, `*.jpg`, `*.log`, `*.wasm`, ソースのバックアップ等）をプロジェクトルート直下に直接出力することを禁止する。
  - すべての一時生成物・テスト用出力は、必ず git で無視される `temp_work/` ディレクトリ配下にのみ書き出すこと。
- **【必須】開発用スクリプト・ツールの配置隔離**:
  - アプリ本番のビルドや実行に直接含まれない検証用・開発用のスクリプト（Python, Shell, Batch, JS 等）およびパッチファイル等は、すべて `scripts/` ディレクトリ配下に配置すること。プロジェクトルート直下に配置することを禁止する。
  - 共有する AI モデルや Kotlin 側から呼び出す必要のあるリソーススクリプトは、正規の `resources/` フォルダ配下に配置すること。
- **【必須】ファイルI/Oにおけるカレント出力の禁止**:
  - プロセス内で一時ファイルを生成・操作する際、ハードコーディングされたルート相対パス（`./`）での出力を禁止する。パス解決クラス（`PathResolver` 等）を介し、`temp_work/` 以下に出力先を限定すること。
- **【必須】クリーン状態の自律検証**:
  - セッション終了前およびコミット前には、必ずルート直下のファイルを点検し、不要なファイルが残存している場合は直ちにクリーンアップすること。

## Clickable Links & Media Rules (Ctrl+クリックでのリンク連携)
- **【必須】Gemini環境におけるファイルパスの生のテキスト出力**:
  - 現在のGemini (Antigravity CLI) 環境では、Markdown形式のリンク（`[表示名](file:///絶対パス)`）はUIのレンダラによって正しくリンク化されず、クリックできなくなる欠陥が存在する。
  - そのため、ユーザーに対してファイル、画像、動画等を提示する際は、Markdownリンクの構文（`[]()`）を**一切使用せず**、**生の絶対パス（Windows形式のバックスラッシュを含む）をプレーンテキストでそのまま出力すること。**
  - IDE（Cursor等）のターミナルやチャットウィンドウは、生のバックスラッシュパス（例: `C:\Users\yuuji\fit-trimmer\...`）を自動的に認識してクリック可能なハイパーリンクに変換する。
  - 正しい例: `C:\Users\yuuji\fit-trimmer\composeApp\temp_work\scan_debug\frame_1000.jpg`
  - 誤った例（機能しない）: `[frame_1000.jpg](file:///C:/Users/yuuji/...)`
- **【厳禁】バッククォートによるリンク無効化の回避**:
  - 生のパスをバッククォート（`` ` ``）で囲むと、IDEの自動リンク認識が壊れて Ctrl+クリックで開けなくなるため、絶対にバッククォートで囲まないこと。

## 物理的な「触る」「観る」による最終確認の義務
- **【必須】「触る（物理的操作）」による動作検証**:
  - テストコード上のモックや論理アサーションのみで完了としてはならない。
  - 実機アプリの起動、またはそれに準ずる通信・ファイル書き込みを伴うシミュレーションプロセスを実際にバックグラウンド実行し、生成されたファイル（SQLite DB、出力動画）が物理的に増加・変容していることを `Test-Path` や SQL クエリによる抽出確認等の「物理的な触診」によって証明すること。
- **【必須】「観る（視覚的目視）」によるレンダリング検証**:
  - UIの表示変更や HUD への描画追加などの視覚的変更を行った場合、必ずその表示結果である「静止画（PNG）や動画フレーム」を absolute path 形式（`file:///...`）でディスク上へ物理出力すること。
  - エージェント自身で OpenCV 等による画像処理検証（VRT等）を行うか、あるいはその画像をマークダウンやログにリンクし、人間（ユーザー）が「Ctrl+クリックで直接目視してデザインを観る」プロセスを最終確認のステップとして必須で介すること。これを行わずに「表示を確認した」と主張することを固く禁ずる。
- **【必須】確認用チェックポイント（CP）の常設**:
  - 各アプリやモジュールの開発において、物理的な「触る」「観る」を最低限のコストで実行できるよう、検証用エントリーポイント（検証スクリプト、デバッグ出力タスク、ダンプAPIなど）を最初からCPとして構築すること。
  - テスト動画・プレビュー画像のワンクリック生成、DB内部状態の即時ダンプ、CURL一発での通信モックシミュレータなどを用意し、検証にかかる手間を極小化する。これはTDDと同等に優先され、サボるための言い訳を封じるためのインフラである。
